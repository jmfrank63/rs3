## Phase Goal

**As a** server operator running rs3, **I want to** rely on a nesting depth limit and an execution timeout for stored scripts, **so that** a self-patching or never-ending script can neither crash the server nor starve other requests.

This plan is the **timeout slice** (ROBU-06). After plan 05-01 a self-patching script is stopped, but `while(true){}` still pins a JS worker forever. Task 1 is the tracer: a runaway top-level script answers 504 `js_timeout` end to end, through the job's termination group, a per-worker watchdog thread, the single classification point and the HTTP error contract, and the worker then serves the next job. Task 2 closes the escapes the research found: a script that catches a nested termination or loops over a throwing op cannot cancel its own termination, writes after the stop are refused, and a late watchdog never hits the next job. Task 3 adds the D-07 backstop for stalls inside Rust and proves that other requests keep being answered while a script loops.

<objective>
Terminate non-terminating scripts after JsSettings.timeout_ms (default 5000, built in code) and answer 504 `{"error":"js_timeout","message":"script exceeded the <ms> ms execution limit"}`. The design is the one the research verified: a per-job JobState with a phase compare-and-swap and an isolate registry, one watchdog thread per worker with 50 ms re-fire, silent ops after the timeout, classification by flag in the executor (host fault > timeout > depth > result), and a backstop of timeout + 2 s that starts at pickup.

Purpose: ROBU-06 and the timeout part of TEST-04, and ROADMAP SC-2/SC-3. A never-ending script costs one worker for at most timeout_ms, and every other request keeps being answered.
Output: Cargo.toml (feature declarations only), src/js/mod.rs, src/js/runtime.rs, src/js/executor.rs, src/js/ops.rs, src/http/error.rs and src/http/mod.rs, plus RED evidence.
</objective>

APIs this plan uses (verified in research against deno_core 0.412.0 / v8 150.4.0):
- `JsRuntime::v8_isolate(&mut self) -> &mut v8::OwnedIsolate`, and `thread_safe_handle()` on it returns a Clone + Send + Sync + Debug `v8::IsolateHandle`.
- `IsolateHandle::terminate_execution(&self) -> bool` can be called from any thread and returns false once the isolate is disposed (harmless).
- A terminated `execute_script` returns `Err` about 1 ms after the call. A terminated script whose remaining code is straight-line can still complete `Ok` (S4b), so the outcome comes from the phase CAS, never from the result.
- A slow op that returns `Err` while its isolate is terminating makes deno_core cancel the termination (S4: `to_v8_error` then `TryCatch::reset`). Hence silent ops after the timeout plus re-fire.
- The worker runs a job outside `block_on` (`rt.enter()` only), so a tokio timer on the worker runtime never fires during a job. The watchdog is a std thread with `std::sync::mpsc::Receiver::recv_timeout`.

//   JsSettings gains `pub timeout_ms: u64` (default 5000)
//   JobState gains: phase: AtomicU8 (0 Running = Default, 1 Finished, 2 TimedOut),

impl JobState {

## Flagged Assumptions

- **A1, PKU on x86_64.** `terminate_execution` from the watchdog thread is assumed safe on the protected platform; the watchdog is spawned from inside its worker so it descends from the thread that called `init_platform` (research Pitfall 10). Proof needs the x86_64 release smoke, which plan 05-03 extends and hands to the operator.
- **A2, Cargo.lock.** Declaring tokio `time` and `macros` leaves Cargo.lock unchanged, because both features are already enabled in the graph and features are not recorded in the lock. Task 3 verifies this with `git diff --exit-code`; if the lock would change, the executor reverts and reports instead of updating it.
- **A3, CI timing.** Normal debug jobs take 21 to 80 ms under 8-thread load on this host. Tests that need a follow-up job to succeed use 250 ms or more. If CI shows false 504s, raise those timeouts to 500 ms.
- **Residual: built-in ops.** A loop over a deno_core built-in op that throws gets a fresh chance to cancel each termination; the 50 ms re-fire makes eventual termination near-certain (research Security Domain). rs3's own ops are silent after the stop.
- **Residual: Rust stalls.** The backstop answers the client, but a worker stuck inside Rust stays busy until the stall ends (Pitfall 11). Heap exhaustion is not covered by the timeout (JSHD-01, deferred). Plan 05-03 documents both; neither is ever tested.
- **D-07 placement.** The backstop lives in `JsExecutor::run_job`, which `patch_key` awaits, as the research responsibility map recommends; the handler itself stays unchanged.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client to stored script | Any client stores and PATCHes scripts; script code is untrusted and runs on a JS worker |
| script to V8 termination | A script can try to catch, cancel or outlast its termination |
| worker to watchdog thread | Cross-thread termination of isolates owned by another job or already disposed |
| request future to worker | The client can disconnect; the worker must still stop the script |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-04 | Denial of Service | JS worker pinned by while(true){} | high | mitigate | Per-worker watchdog fires terminate_execution on every registered isolate at timeout_ms (Task 1); timeout_infinite_loop_is_504_then_worker_serves_next and timed_out_worker_serves_next_job prove the worker is freed |
| T-05-05 | Denial of Service | Catch-and-continue around a terminated nested PATCH, or a loop over a throwing op, cancels the termination (research S4/S5) | high | mitigate | rs3 ops go silent after the timeout and never throw; op_rs3_patch returns an empty string after a terminated nested run; the watchdog re-fires every 50 ms until disarmed (Task 2 regression tests for S4, S5, S8) |
| T-05-06 | Tampering | A late watchdog terminates or misclassifies another job | medium | mitigate | Each job owns its Arc<JobState> and isolate list; fire() only acts on a Running or TimedOut job; the worker disarms before the next job (late_watchdog_never_hits_next_job, job_state_phase_changes_exactly_once) |
