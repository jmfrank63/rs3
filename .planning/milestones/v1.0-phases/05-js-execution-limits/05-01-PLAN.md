## Phase Goal

**As a** server operator running rs3, **I want to** rely on a nesting depth limit and an execution timeout for stored scripts, **so that** a self-patching or never-ending script can neither crash the server nor starve other requests.

This plan is the **depth-limit slice** (ROBU-05). Today a script that PATCHes itself, directly or through a cycle of keys, recurses until about 800 MB of nested runtimes later. Task 1 is the tracer: an over-deep PATCH chain answers 422 `js_depth_limit` end to end, through op_rs3_patch, the per-job state, the executor's single classification point and the HTTP error contract. Direct self-patching and an A -> B -> A cycle are then stopped with the exact key chain. Task 2 makes the stop a hard stop: ops refuse after it, a caught error still answers 422, writes before the stop stay, and the stop is logged once. Task 3 lets the operator tune the limit in code within a safe clamp and pins the research flag on stack use at the maximum depth. The timeout comes in plan 05-02.

<objective>
Stop self-patching and cyclic PATCH chains with a nesting depth limit (default 4, JsSettings, clamped 1..=64). The limit is checked in op_rs3_patch before the next key is read, recorded in a shared per-job JobState, classified once in the executor (host fault > depth > script result) and answered as 422 `{"error":"js_depth_limit","message":"PATCH nesting depth limit (4) exceeded: <chain>"}`, even when the script catches the error.

Purpose: ROBU-05 and the depth part of TEST-04. The server stays up and answers in milliseconds instead of spending 800 MB and seconds per request.
Output: src/js/mod.rs, src/js/ops.rs, src/js/runtime.rs, src/js/executor.rs, src/http/error.rs and src/http/mod.rs, plus RED evidence under .planning/phases/05-js-execution-limits/tdd-evidence/.
</objective>
